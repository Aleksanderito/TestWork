# Часть 1. Обработка кандидатов `super_boss`

Небольшой Python-сервис для обработки кандидатов, у которых установлен пользовательский признак:

```text
super_boss = true
```

Основная задача  — автоматически изменить название должности таких кандидатов, добавив к нему суффикс:

```text
 — Супер Босс
```

Например:

```text
Менеджер по продажам
```

превращается в:

```text
Менеджер по продажам — Супер Босс
```

При этом повторный запуск программы не добавляет суффикс второй раз.

---

## Что делает программа

При запуске приложение выполняет следующие шаги:

1. Получает список всех кандидатов с признаком:

```text
super_boss = true
```

2. Проверяет текущее название должности каждого кандидата.

3. Если должность ещё не заканчивается на:

```text
 — Супер Босс
```

программа добавляет этот суффикс.

4. Сохраняет новое название должности через интеграционный слой.

5. Записывает информацию о выполненных действиях в аудит-журнал формата JSON Lines.

Например:

```text
Менеджер по продажам
```

после обработки станет:

```text
Менеджер по продажам — Супер Босс
```

Если программа будет запущена повторно, значение останется таким же.

---

## Архитектура

Бизнес-логика приложения отделена от способа подключения к WebTutor.

Основная обработка находится в:

```text
SuperBossProcessor
```

`SuperBossProcessor` не знает, каким именно способом происходит получение и сохранение кандидатов.

За работу с внешней системой отвечает интерфейс:

```text
CandidateRepository
```

Он содержит два основных метода:

```python
get_super_boss_candidates()
```

Получает кандидатов с признаком:

```text
super_boss = true
```

и:

```python
update_position(candidate_id, position_name)
```

сохраняет новое название должности кандидата.

Такое разделение позволяет оставить бизнес-логику без изменений и заменить только интеграционный слой.

Например, в реальной системе вместо тестового репозитория можно использовать:

```text
SuperBossProcessor
        │
        ▼
CandidateRepository
        │
        ├── FakeCandidateRepository
        │
        ├── REST API
        │
        ├── SOAP API
        │
        └── другой доступный интерфейс WebTutor
```

Какой именно транспорт будет использоваться для реальной интеграции, зависит от интерфейсов, доступных в конкретной установке WebTutor.


## Запуск

Для работы требуется Python 3.

Из корня проекта выполнить:

```bash
python main.py
```

После запуска программа:

1. получит кандидатов;
2. обработает записи с `super_boss = true`;
3. изменит необходимые должности;
4. сформирует аудит-журнал;
5. выведет итоговую статистику.

Пример:

```text
found=4 updated=2 skipped=2 failed=0

Candidates after processing:
1: 'Менеджер по продажам — Супер Босс'; super_boss=True
2: 'Разработчик'; super_boss=False
3: 'Директор — Супер Босс'; super_boss=True
4: 'Аналитик — Супер Босс'; super_boss=True
5: ''; super_boss=True
```

Значения означают:

```text
found    — количество найденных кандидатов с super_boss = true
updated  — количество изменённых кандидатов
skipped  — количество кандидатов, которых менять не потребовалось
failed   — количество ошибок обновления
```


## Пример записи аудита

При успешном изменении кандидата в журнал может быть записано:

```json
{
  "timestamp": "2026-08-18T11:00:00+03:00",
  "event": "candidate_updated",
  "run_id": "...",
  "user": "test-user",
  "candidate_id": 1,
  "old_value": "Менеджер",
  "new_value": "Менеджер — Супер Босс",
  "status": "success"
}
```

Здесь:

* `timestamp` — время события;
* `event` — тип действия;
* `run_id` — идентификатор конкретного запуска;
* `user` — пользователь или системный инициатор;
* `candidate_id` — идентификатор кандидата;
* `old_value` — значение до изменения;
* `new_value` — значение после изменения;
* `status` — результат операции.

---

## `run_id`

Каждый запуск программы получает уникальный:

```text
run_id
```

Он добавляется ко всем событиям аудита этого запуска.

Например:

```text
run_id = 8f04c1...
```

может присутствовать в событиях:

```text
job_started
candidate_updated
candidate_skipped
candidate_update_failed
job_finished
```

Благодаря этому при анализе журнала можно определить, какие действия относились к одному конкретному запуску программы.

---

## Типы событий

В аудит могут записываться следующие события:

```text
job_started
```

Начало обработки.

```text
candidate_updated
```

Должность кандидата успешно изменена.

```text
candidate_skipped
```

Кандидат не требует изменения, например потому что суффикс уже присутствует.

```text
candidate_update_planned
```

Изменение было определено программой как необходимое.

```text
candidate_update_failed
```

При сохранении кандидата произошла ошибка.

```text
job_finished
```

Обработка завершена.

## Пример сценария

Предположим, в системе есть следующие кандидаты:

```text
1. Менеджер              super_boss=true
2. Разработчик           super_boss=false
3. Директор — Супер Босс super_boss=true
4. Аналитик              super_boss=true
```

После выполнения программы:

```text
1. Менеджер — Супер Босс
2. Разработчик
3. Директор — Супер Босс
4. Аналитик — Супер Босс
```

Кандидат №2 не обрабатывается, потому что:

```text
super_boss=false
```

Кандидат №3 не изменяется, потому что нужный суффикс уже присутствует.

Кандидаты №1 и №4 будут обновлены.

## Подключение к WebTutor

Текущая реализация специально не привязана к конкретному механизму интеграции WebTutor.

Для подключения реальной системы необходимо реализовать `CandidateRepository`, например:

```python
class WebTutorCandidateRepository(CandidateRepository):
    def get_super_boss_candidates(self):
        # получение кандидатов из WebTutor
        ...

    def update_position(self, candidate_id, position_name):
        # сохранение изменений в WebTutor
        ...
```

После этого новый репозиторий передаётся в `SuperBossProcessor`.

Сама бизнес-логика при этом остаётся без изменений.

## Итог

разделение приложения на две основные части:

```text
Бизнес-логика
     │
     ▼
SuperBossProcessor
     │
     ▼
Интеграционный интерфейс
CandidateRepository
     │
     ▼
WebTutor / Fake Repository
```

Такой подход позволяет сначала проверить алгоритм на моковых данных, а затем подключить реальный WebTutor, заменив только реализацию интеграционного слоя.
Потенциально вижу этот дополнительный модуль со своим графическим интерфейсом для внедроения в общий фуниконал.
